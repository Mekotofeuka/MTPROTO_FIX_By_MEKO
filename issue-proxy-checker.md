# proxy_checker.py: два бага дают ложное «PQ не поддерживается» для полностью рабочего домена

## TL;DR

Чекер сообщает, что домен не поддерживает `X25519MLKEM768` и что «Обычное TLS не удалось», хотя домен всё поддерживает, а прокси работает. Обе ошибки — на стороне чекера:

1. **Хардкод `OPENSSL_BIN = "/usr/bin/openssl"`** (строка 21) — на Ubuntu 24.04 это OpenSSL 3.0.13, который не знает ML-KEM. Установить 3.5 в `/usr` на 24.04 штатно невозможно, поэтому его собирают в отдельный префикс — и чекер его не видит.
2. **Отсутствие пауз между вызовами `run_openssl()`** — 2-3 подключения подряд попадают под hashlimit самого MEKO-фикса (54/minute + REJECT) и получают `Connection refused`.

Второй баг воспроизводится **на любом сервере с установленным фиксом** — то есть у всей целевой аудитории репозитория.

---

## Баг 1. Хардкод пути к openssl

### Описание

```python
# proxy_checker.py:21
OPENSSL_BIN = "/usr/bin/openssl"
```

На Ubuntu 24.04 LTS по этому пути — **OpenSSL 3.0.13**. Поддержка `X25519MLKEM768` появилась только в ветке **3.5**. В репозиториях Ubuntu 24.04 её нет и не будет (LTS не меняет мажорные версии библиотек), а подмена системной libssl ломает apt/ssh/systemd. Штатный путь — сборка из исходников в отдельный префикс (`/opt/openssl-3.5`, `/usr/local`). Хардкод делает такую установку невидимой для чекера.

Показательно: шапка меню `mekopr` (строки 1229–1244) определяет версию через `command -v openssl` и корректно выводит зелёным `3.5.7`. Пользователь видит «OpenSSL: 3.5.7» — и одновременно получает ошибку про неподдерживаемую группу. Симлинки, `PATH`, `sudo` на это не влияют: путь прибит гвоздями.

### Воспроизведение

Ubuntu 24.04, системный OpenSSL 3.0.13, собранный 3.5.7 в `/opt/openssl-3.5`:

```bash
$ openssl version
OpenSSL 3.5.7 9 Jun 2026 (Library: OpenSSL 3.5.7 9 Jun 2026)
$ sudo openssl version
OpenSSL 3.5.7 9 Jun 2026
$ openssl list -tls-groups | grep -o X25519MLKEM768
X25519MLKEM768
```

Запускаем `sudo mekopr` → проверка прокси:

```
━━━ Короткая проверка по IP ━━━
  🟡 <ip> — PQ нет, маркер НЕТ
━━━ PQ-подключение ━━━
🔸 Статус: не поддерживается
  Причина: ...:error:0A080106:SSL routines:gid_cb:passed invalid argument:../ssl/t1_lib.c:750:group 'X25519MLKEM768' cannot be set
```

Оба вердикта ложные, причём по разным механизмам:

- **PQ-подключение**: `gid_cb` — парсер списка групп внутри OpenSSL. Ошибка возникает при разборе `-groups`, **до отправки ClientHello**. Запрос к серверу не уходит вообще.
- **Короткая проверка по IP**: `-groups` не использует, поэтому не падает — но 3.0.13 не кладёт гибридную группу в ClientHello. Сервер закономерно выбирает x25519, чекер пишет «PQ нет».

### Ожидаемо

Та же проверка бинарником 3.5.7:

```bash
$ echo | /opt/openssl-3.5/bin/openssl s_client -connect <host>:<port> \
    -servername <host> -groups X25519MLKEM768 2>&1 | grep -i "Negotiated TLS1.3 group"
Negotiated TLS1.3 group: X25519MLKEM768
```

После правки строки 21 на путь к 3.5.7 короткая проверка сразу даёт `🟢 PQ OK`.

## Баг 2. Чекер попадает под rate limit собственного фикса

### Описание

`run_openssl()` вызывается подряд без пауз (строки 126, 148, 286, 293, 369, 400, 437, 483). MEKO-фикс, как описано в README, ограничивает входящие SYN до **54/minute (≈1.1 сек) на IP** и отвечает **REJECT с tcp-reset**. Ядро на стороне клиента превращает RST в `ECONNREFUSED`.

Результат: первая проверка проходит, все последующие в пределах ~1.1 сек получают отказ.

### Воспроизведение

Целевой сервер: MTProto + MEKO-фикс. Проверяющая машина: **любая**, Ubuntu 24.04, openssl 3.5.7, чекер уже пропатчен (баг 1 устранён).

```
━━━ Короткая проверка по IP ━━━
  🟢 213.x.x.x — PQ OK                      ← прошла
━━━ PQ-подключение ━━━
🔸 Статус: не поддерживается
  Причина: ...:error:8000006F:system library:BIO_connect:Connection refused:crypto/bio/bio_sock2.c:183:calling connect()
━━━ Обычное TLS-подключение ━━━
❌ Обычное TLS не удалось                    ← отказ
```

Изолированно, тем же бинарником, тот же домен и порт — **без пауз**:

```
попытка 1: X25519MLKEM768
попытка 2: refused
попытка 3: refused
```

**С паузами `sleep 2`** — три успеха подряд.

Проверено с двух независимых VPS (разные IP, разные провайдеры). Сигнатура идентична: первая проверка ✅, вторая и третья ❌. Лимит per-source-IP, поэтому смена машины ничего не меняет — она лишь выдаёт новое ведро того же объёма.

Счётчики на сервере подтверждают: `iptables -L INPUT -n -v | grep REJECT` прирастает ровно на 2 за прогон чекера.

### Почему это заметно не сразу

В примерах README фигурируют чужие домены (`rutube.ru`), у которых лимита нет. При проверке **собственного прокси с установленным фиксом** чекер спотыкается о то, что диагностирует. До исправления бага 1 это маскировалось: PQ-проверка падала на парсинге `-groups` и SYN не отправляла — лимит «съедала» только третья проверка, отсюда стабильное «Обычное TLS не удалось» во всех прогонах.

## Предлагаемое исправление

PR прилагается. Кратко:

1. **Автоопределение openssl** вместо хардкода — с приоритетом сборок ≥3.5, проверкой через `list -tls-groups` (надёжнее парсинга строки версии: отвечает ровно на нужный вопрос и не ломается о суффиксы `-dev`/`+quic`), переопределением через `MEKO_OPENSSL_BIN` и фолбэком на системный бинарник.

2. **Явная диагностика вместо молчаливого ложноотрицания.** Если ни один найденный бинарник не знает `X25519MLKEM768` — не выносить вердикт о сервере, а сообщить, что проверка невозможна:
   ```
   ⚠️  Локальный OpenSSL 3.0.13 не поддерживает X25519MLKEM768.
       Результат PQ-проверки недостоверен. Требуется OpenSSL >= 3.5.
   ```
   Сейчас пользователь получает вердикт о сервере там, где проблема на клиенте, и начинает менять рабочий домен.

3. **Отдельная обработка `gid_cb`** — эта ошибка означает «клиент не умеет группу», а не «сервер её отверг». Семантика принципиально разная, смешивать их нельзя.

4. **Троттлинг ≥1.2 сек** между вызовами `run_openssl()` — компенсирует hashlimit фикса. Проверка станет медленнее на ~4 сек; приемлемая цена за достоверность.

5. **Распознавание `Connection refused`** как вероятного срабатывания rate limit, с подсказкой пользователю, а не как «сервер не поддерживает».
